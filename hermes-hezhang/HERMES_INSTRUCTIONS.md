# 合掌QQ联机工具（Hermes运行说明）

你是合掌QQ机器人的消息协调员，不是规则裁判。所有房间状态和结算必须调用本目录的HTTP服务；不得凭聊天上下文推测、补写或修改生命、锻数、行动与结果。

`docs/合掌网页版统一规则.md`用于向玩家解释规则和后续开发核对；当前服务实际支持范围以本文件“当前支持范围”和`/health`返回的规则集标识为准。

## 架构（2026-08-11 更新）

- 消息通道：`hezhang_gateway_qq.py`（独立 Python 守护进程，直连 QQ WS，不经 Hermes 中转）负责解析玩家指令并调用 Node 裁判服务。
- 规则裁判：`src/server.mjs`（HTTP 127.0.0.1:3217），状态落盘 `data/hezhang-state.json`。
- Hermes 不直接参与合掌消息收发；本文件供人工维护与排查参考。

## 启动

1. 确认云电脑安装 Node.js 20 或更高版本。
2. 将`config.example.json`复制为`config.json`，把`adminToken`换成长随机字符串。
3. 将`hezhang-gateway.example.json`复制为`hezhang-gateway.json`，填写QQ凭据，并令`admin_token`与Node配置一致。
4. 执行`python -m pip install -r requirements.txt`安装网关依赖。
5. 双击`start.cmd`启动Node服务，再双击`start-gateway.cmd`启动QQ网关。
6. 请求`GET http://127.0.0.1:3217/health`确认`ok:true`。
7. 将两个服务设置为云电脑开机自启；`config.json`和`hezhang-gateway.json`均不得发到GitHub或聊天中。

除`/health`外，请求头必须包含：

```text
Authorization: Bearer <confi...ken>
Content-Type: application/json
```

## QQ身份规则（全私聊模式）

- `userId`必须使用QQ机器人平台返回的稳定内部用户ID，不使用昵称。
- `name`只用于显示。
- `eventId`使用QQ入站事件ID，用于避免重复消息造成二次提交。
- **全私聊**：所有玩家操作只接受私聊（C2C）；群内命令一律引导玩家私聊机器人，不在群内处理任何指令。
- 结算结果只私聊发给参战双方，不在群内广播。
- 不得在结算前把任何玩家的行动发送给其他人。

## HTTP接口

### 创建房间

`POST /rooms`

```json
{"ownerId":"u1","ownerName":"甲","mode":"duo","teams":2,"hp":1,"attack":1,"energy":0,"shield":0,"scissors":true}
```

- `mode` 目前仅支持 `duo`（双人）；传入 `multi` 返回“多人模式暂未开放”。
- 房间属性：`hp`（1-20，初始生命）、`attack`（0-10，初始攻击力=命中伤害）、`energy`（0-10，初始锻数）、`shield`（0-10，初始护盾层数，每层挡一次非真实伤害）。
- `scissors`控制双人剪刀模式，默认`true`；关闭后服务端不会列出或接受剪刀。
- 双人默认 `1/1/0/0`（HP/攻击/锻/盾）；`teams` 固定为2。

### 加入房间

`POST /rooms/123456/join`

```json
{"userId":"u2","name":"乙","team":1}
```

队伍从0开始编号。房间最多2人；第三人加入返回“双人对局房间已满”。

### 开始

`POST /rooms/123456/start`

```json
{"userId":"u1"}
```

### 查询玩家视图

`POST /rooms/123456/view`

```json
{"userId":"u1"}
```

只把返回值中的`you`和`legal`私发给该玩家；公共`room`不含平台内部用户ID，仅用于展示和排障。

### 取得私聊收件人（受信网关专用）

`GET /rooms/123456/recipients`

返回参战者内部ID，仅供本机受信网关发送私聊。不得把结果转发给玩家、写入战报或公开日志。

### 提交行动

`POST /rooms/123456/submit`

```json
{"userId":"u1","move":"forge","eventId":"qq-event-001"}
```

行动键：`forge`锻造、`defend`防、`catch`接、`flash`闪、`knife`小刀、`scissors`剪刀、`katana`武士刀、`shuriken`手里剑、`kunai`苦无、`dragon`龙牙、`void`虚无。

当`resolution`为`null`时，只回复“行动已秘密提交，等待N人”。有结算时，把`resolution.events`按原顺序完整私聊发给参战双方，不得删改规则解释。

### 删除大厅房间（管理用）

`DELETE /rooms/123456`

```json
{"userId":"u1"}
```

仅房主可删除`status=lobby`的房间；对局中（playing）或已结束（finished）房间拒绝。

### 导出战斗记录

`GET /rooms/123456/export`

仅允许 `status=finished`（对局结束）的房间；返回房间配置、参战玩家与完整 `log` 战斗记录。对局中返回“对局未结束，暂不能导出战斗记录”。

## 当前支持范围

规则集标识为`base-online-v3`（2026-08-12，双人剪刀版）：

- **仅双人对局**（2人、2队各1人，队伍自动分配：房主队1，加入者队2）；
- 默认所有敌对阵营共同判刀；
- 支持锻造、防、接、闪与六种基础武器；
- 支持双人可选剪刀模式：剪刀胜小刀、武士刀、手里剑、接；负于锻造、苦无、龙牙、虚无；防只挡住，闪成功重开，双剪刀相抵；
- 支持三级以上敌对阵营同级抵刀；
- 支持攻击动作防御等级、逐级判刀、一人每次出手至多被普通武器命中一次；
- 支持虚无向所有合法敌人分别结算；
- 支持建房配置HP、攻击力、初始锻数和本体护盾；0攻击力必须造成0伤害；
- 支持重开清锻、死亡、胜负和平局；
- 状态落盘，进程重启后可以恢复；长期无活动房间和事件去重记录按`roomIdleHours`清理。

暂不支持36名角色技能、多人模式、帮接／帮闪／主动承受的人工选择、月亮防反、怪兽猜拳和审判追加对局。后续多人协议必须实现普通攻击中的帮助赌博：不帮助时接／闪使用者本人必定安全、其余角色继续判刀；帮助时当前刀完整防住、无人受伤并统一重开，但帮助者放弃自保。极光复制攻击不得开放帮接／帮闪窗口，但仍可处理主动承受。玩家询问时必须如实说明当前联机版范围，不能由AI临时模拟。

网关交互约束：指令按钮必须发送完整命令，但解析时显式六位房间号要先从后续动作参数中移除；“对手已出招”提醒只允许发送给尚未提交且确有其他存活玩家已经提交的玩家。两条逻辑集中在`gateway_logic.py`并由Python单元测试覆盖。

## 推荐QQ命令（全私聊）

```text
/创建 [HP 攻 锻 盾] [剪刀开|剪刀关]   # 缺省 1 1 0 0 剪刀开
/加入 <房间号>
/开始 <房间号>        # 房主开局，向每一位房内玩家广播
/出招 <房间号> <招式>
/状态 <房间号>
/记录 <房间号>        # 对局结束后导出战斗记录（分段私聊发送）
/规则
```

流程：房主私聊`/创建 [配置]`拿到房间号 → 房主把房间号发给对手（微信群/QQ消息自行传播）→ 对手私聊`/加入 <房间号>` → 房主私聊`/开始 <房间号>`（全员广播开局）→ 双方私聊`/出招 <房间号> <招式>` → 结算私聊送达双方 → 对局结束后任一方`/记录 <房间号>`导出战斗记录。

兼容旧前缀：`/合掌 创建` 等旧写法仍可解析，但群内一律无效。

招式别名：锻造/锻、防/防御、接/格挡、闪/闪避、小刀、剪刀、武士刀、手里剑、苦无、龙牙、虚无；原有数字别名0-9保持不变，剪刀使用中文或✂符号，避免破坏既有数字映射。

Hermes可以理解自然语言，但最终必须映射到上述接口和固定行动键。信息不足时先询问，不得猜测房间、队伍或行动。
