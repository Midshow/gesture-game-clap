## 1. 阶段一：剪刀模式（✅ 2026-08-12完成）

**目标**：双人对局可选剪刀，完整克制表。

**规则要点**（规则总典 §第一编）：
- 剪刀：1 锻、特殊 1.5 级攻击；**克制** knife/katana/shuriken/catch；**被** forge/guard/kunai/dragonFang/void **克制**；对 flash 触发闪成功重开；双人剪刀相抵
- 仅双人可用（多人禁用）

**实现点**：
1. `src/rules.mjs`：`MOVES` 增加 `scissors`（type:attack, cost:1, level:1.5）；`resolveStep` 增加剪刀特殊判定分支（剪刀参与判刀但用克制表而非等级比较）
2. 房间配置增加 `scissors: true/false`（建房参数或默认开启）；建房时可选
3. 网关：`MOVE_ALIAS` 加 "剪刀"；出招按钮组加剪刀键（10→11 键布局）
4. 测试：剪刀克制表全用例（胜 4、负 4、闪重开、双剪刀相抵）

**完成情况**：`MOVES`、双人专用克制结算、房间开关、QQ别名与条件按钮均已实现；Node自动测试覆盖胜4、负4、防、闪、双剪刀及左右对称。由于本地没有QQ测试凭据，本次只完成网关静态契约与语法验证，部署后的QQ按钮实测仍需运维人员执行。

## 2. 阶段二：技能系统第一批（无交互被动）

**目标**：先实现不需要玩家中途选择的被动技能，验证事件钩子架构。

**建议技能顺序**（由易到难）：
| 技能 | 机制 | 所需钩子 |
|---|---|---|
| 死神 | 造成伤害后 生命+1 攻击+1 | on-damage-dealt |
| 暴君 | 生命≤1 时伤害=10 | damage-modify |
| 猎人 | 死亡后由猎人本人选人并造成1真伤 | on-death + 真伤标志 + 暂停结算选择协议（移至阶段四） |
| 太阳 | 伤害全为真伤 | 真伤标志 |
| 战士 | 武士刀破防且伤害=0.5 | damage-modify + 0.5 体系 |
| 刺客 | 小刀首命 +0.5；防可挡手里剑 | on-hit + 防御扩展 |
| 守卫 | 防/接获得 0.25/0.5 锻 | on-defense + 0.5 锻 |
| 壁垒 | 1 锻大盾防除虚无外攻击 | 新行动键 |
| 白塔 | 首次武器返还花费 | on-pay |
| 窥秘人 | 龙牙/虚无 -1 锻 | cost-modify |
| 囚徒 | 闪 -2 攻 +1；成功闪偶数次攻击永久-1 | cost-modify + 计数 |

**架构要求**：
1. **引入轻量事件分发**（参考单机版 `SkillTiming`，但用确定性种子 RNG）：`on-hit / on-damage / on-death / on-round-end` 钩子挂在 `resolveStep` 中，技能以注册表方式挂接，禁止散落 if
2. **技能字段入玩家对象**：`skills: {reaper: {...}, ...}`，重开/重开房间时按规则保留或清除
3. **真伤标志**：`damage.true = true` 绕护盾直接扣本体
4. **0.5 体系**（若战士/守卫/刺客先做）：建议内部数值 ×4 整数化（0.25→1、0.5→2、1→4），展示层除 4——避免浮点误差；不得用取整近似规则数值

**验收**：每个技能独立单测；`npm test` 全绿；与单机版 v2.5.7 行为对照（差异清单 §7 第一批）。

## 4. 阶段四：交互协议（多人前奏，最大工程量）

**背景**：怪兽猜拳、魔术师改写、审判追加对局、帮接/帮闪、主动承受都需要**玩家在结算中途决策**。当前 `resolveStep` 是同步函数，无法 await 玩家选择。

**设计建议**：
1. Node 服务引入**两阶段结算**：`submit` 触发判刀 → 若存在需玩家决策的窗口，返回 `resolution: {pending: true, question: {...}, candidates: [...]}`，房间状态置 `awaiting` 并挂起
2. 网关收到 pending → 向相关玩家私聊发选择按钮/文本 → 玩家回复 → 网关调 `POST /rooms/{id}/resolve` 提交决策 → 继续结算直至完成
3. 所有决策窗口必须**可超时**（如 60s 未答复 → 自动随机/默认选择，防卡局）
4. 事件顺序遵循规则总典 P0-P12 优先级表

**优先实现**：
- 怪兽猜拳（猜拳交互，最简单）
- 魔术师改写（选择目标）
- 猎人死亡选人（由死亡的猎人本人选择，不能自动或由房主代选）
- 审判追加对局（递归小对局，复杂度高，可最后）

**验收**：完整对局含猜拳/改写不卡死；超时自动处理；日志完整。

## 5. 阶段五：多人模式开放

**目标**：解除 duo 锁定，支持 2-12 人 / 2-6 队（每队 1-4 人）。

**实现点**：
1. `game.mjs` create 放开 `mode=multi`、teams 2-6；join 放开 2 人上限；start 检查阵营数
2. 判刀引擎已支持多人（防御等级覆盖、3 级抵刀、命中上限、虚无多目标）——回归验证
3. **帮接/帮闪（帮助赌博）**：按规则总典 §第三编——不帮则自保、帮则防全刀弃自保；极光复制攻击禁帮防；需要阶段四交互协议
4. **主动承受（帮吃）**：与帮接/帮闪区分；被选中立即占判刀名额
5. 领域技能（极光/观众/黑夜/牧羊人）随技能系统
6. 网关：建房配置按钮/参数扩展（队数）；多人房间视图

**验收**：多人回归测试（抵刀/命中上限/虚无/多队）；帮防交互协议实测。

## 7. 工程红线（改代码必守）

1. **确定性**：一切随机用种子 RNG（`rules.mjs` 的 `rng(hashSeed(...))`），禁止 `Math.random()`
2. **隐私**：`publicRoom`/`listRooms` 永不暴露玩家 id；私聊收件人只经 `recipients` 接口
3. **安全**：`config.json`/`hezhang-gateway.json` 不外发；接口带 adminToken 鉴权
4. **可回滚**：改前备份；测试先行（`npm test` 同时运行Node与Python回归）
5. **同步方法**：单元测试中同步抛错用 `assert.throws`，异步用 `assert.rejects`
6. **部署**：改代码后重启 `Hermes_Hezhang`（Node）与 `Hezhang_Gateway`（Python）两个计划任务；`rooms` 是 map 非数组（脚本读取用 Node 解析）
