## 发现的问题

### [P1] 多人“帮吃”仍执行已经过时的锻造人数规则

位置：v2.5.7 第 3321—3340 行，尤其是 `canHumanVolunteerMp()`。

当前程序只有同时满足下列条件时才向玩家提供主动承伤：

- 玩家行动必须是“锻造”；
- 敌方攻击数量必须大于本队锻造者数量。

统一规则的现行口径是：只要玩家处于当前这把刀的原判刀范围、本回合尚未承受过武器攻击、仍然存活且能够被该刀命中，就可以选择自己帮吃。规则没有要求玩家必须锻造，也没有“攻击数大于锻造者数”的门槛。

影响：玩家使用接、闪、防或其他仍可能被当前攻击命中的行动时，可能被错误剥夺帮吃资格；即使玩家锻造，只要旧的计数条件不满足，也无法按现行规则主动承伤。这会直接改变多人组队对局的判刀结果。

建议修复：资格判断只使用传入的原判刀候选集、存活/退场状态和 `judgementHitThisRound`；不要再检查行动是否锻造或全场攻击/锻造数量。若玩家选择帮吃，应与所有 AI 帮吃者一起进入帮助者池，而不是无条件直接指定玩家承受。

建议测试：覆盖玩家分别使用锻造、防、接、闪且均处于合法候选范围的情形；覆盖已占用判刀名额、动作防御等级已覆盖攻击、已退场和不在原范围时不能帮吃；覆盖玩家和一名 AI 同时帮吃时必须在两者间随机。

### [P1] 玩家死亡后由队友赢得比赛，会被显示为“AI 阵营获胜”

位置：v2.5.7 第 3590—3598 行，`checkMpWinner()`。

当前胜利变量为：

```js
const won = teams[0] === 0 && getHuman().alive;
```

如果真人玩家已经死亡，但其 0 队 AI 队友最终获胜，`teams[0] === 0` 为真、`getHuman().alive` 为假，因此界面显示“比赛结束，AI阵营获胜”，结果印章也按失败展示。

统一规则明确规定玩家死亡但队友仍存活时比赛继续；最终胜负属于阵营。玩家本人是否存活不应改变 0 队的获胜归属。

影响：比赛的数值结算可能正确，但最终结果、状态文字、结果弹窗和分享战报会错误描述胜方。

建议修复：组队和多队模式下以 `teams[0] === getHuman().team` 判断玩家阵营是否获胜。若产品希望区分“本人存活获胜”和“队友代赢”，应作为次级描述显示，不能把玩家阵营胜利改成 AI 胜利。

建议测试：玩家淘汰、同队 AI 存活并最终击败其他队伍；验证状态栏、弹窗标题、印章和分享结果均为玩家阵营获胜。

### [P2] 回合开始效果产生决胜分后，不会立即结束标准赛

位置：v2.5.7 第 1403—1418 行，`ensureDuelRoundStarted()`。

回合开始阶段若低血量死亡、梦魇或其他开始阶段效果导致角色死亡，函数会：

- 增加比分；
- 重建角色；
- 进入下一回合；
- 重新启动计时。

但该路径没有执行与正常结算第 1592 行等价的目标胜分检查。因此，如果这次死亡让一方达到标准赛目标分，比赛仍继续，玩家还可以再进行回合。

建议修复：把“标准赛是否达到目标胜分”的判断提取为统一函数，让正常出手死亡和回合开始死亡共用。

建议测试：比分为目标分减一时，由回合开始死亡结算产生最后一分，必须只弹出一次结束界面且不能继续出招。

### [P2] 包含系统战报时，分享双人战报可能抛出异常

位置：v2.5.7 第 2136—2165 行，`shareResultCard()`。

回合开始技能造成死亡时，程序会插入 `item.system === true` 的战报项。这类项目没有 `player`、`ai`、`before` 和 `after` 字段。但分享图片循环无条件执行：

```js
skillMove(item.player).name
skillMove(item.ai).name
item.before.playerEnergy
```

当最近七条记录中包含系统项时，`skillMove(undefined)` 返回 `undefined`，随后读取 `.name` 会抛出异常，导致分享图片无法生成。普通页面战报渲染已经针对 `item.system` 分支处理，但分享函数没有同样的分支。

建议修复：分享循环中为系统项绘制独立模板，或先把日志统一转换成安全的展示模型；`topMoveName()` 也应忽略没有合法 `player` 招式的系统项。

建议测试：构造一条回合开始死亡系统日志，调用分享数据格式化逻辑，验证不抛错且图片文字包含系统事件。

### [P2] 统一规则 DOCX 与 Markdown 并不完全相同

审查得到：两种格式均可归纳为 324 个正文/表格内容块，但有 5 个块内容不同。Markdown 和 HTML 内嵌规则一致，DOCX 相对落后或存在措辞错误。

差异涉及：

- 普通技能自损与先驱失血的“受到伤害”定义；
- 优先级表 P5 的月亮防反范围；
- 月亮防反段落中的连接词及友伤表述；
- 先驱面对范围效果和正数伤害时的补充说明；
- 月亮角色条目的小刀、虚无和友伤表述。

其中 DOCX 还出现“防反保留闪的花费，但不继承普通闪的防御等级限制，但结算优先级……”的重复“但”，Markdown 已改为分号。

影响：两份名义上相同的程序蓝本会向开发者和规则审核者提供不同的细节，尤其会影响先驱受到伤害响应和月亮防反。

建议：确认 Markdown 是否为最新权威工作稿；若是，从 Markdown 重新生成 DOCX，并把一致性检查加入规则发布流程。目前 HTML 的 `EMBEDDED_RULEBOOK_MD` 已由测试保证与 Markdown 完全一致。

### [P3] 现有“帮吃”测试固定了旧规则，而非当前统一规则

位置：`tests/v2.5.5-volunteer-monster.test.mjs`。

该测试明确断言：防御中的真人不能主动承伤、锻造者只有在敌方攻击数大于本队锻造数时才能帮吃。这与 2026-08-03 统一规则不一致，而且测试对象仍是 v2.5.5，不是 v2.5.7。

影响：测试虽然通过，却会给维护者造成“当前帮吃规则已经验证”的错误印象；将来按统一规则修复时，该旧测试还可能阻止正确修改。

建议：保留历史版本测试时在名称和说明中明确“只冻结 v2.5.5 历史行为”；另为 v2.5.7 新建基于现行统一规则的行为测试。

### [P3] README 和版本说明尚未切换到 v2.5.7

`README.md` 仍把 v2.5.6 标为当前推荐正式版，正式版本说明也只记录到 v2.5.4 的细节。发布 v2.5.7 前应补充下载链接、主要修复内容、规则蓝本说明和测试命令。

### [P3] 计时设为 0 秒时会产生无效进度条宽度

位置：v2.5.7 第 2186—2198 行。

当开启计时且秒数为 0 时，进度计算的分母为 `timerSeconds * 10`，即 0；首次定时器回调会写入 `NaN%`。随后仍会自动选择“防”，所以通常不会阻断游戏，但状态表达不干净。

建议：明确 0 秒的产品含义。若表示“不计时”，应直接不启动定时器；若表示立即自动出招，应绕过进度计算并直接安排一次安全的异步出招。

- 多人攻击建立、动作防御等级、月亮防反先于抵刀、三级以上抵刀、同级随机处理、0 伤害不耗盾等关键规则均有明确实现痕迹和专项测试。
